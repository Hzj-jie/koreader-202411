# Project Rules

*   **Pre-commit Code Formatting**: Do NOT run `./runstylua.sh` on feature branches or during regular commits, as it formats the entire repository and introduces unrelated changes and merge conflicts. Only run `./runstylua.sh` on `master` as its own dedicated `style: run runstylua.sh` cleanup commit after feature PRs land.
*   **Static Code Analysis (Linter)**: Before committing any changes, run the `./runluacheck.sh` script to check for linter warnings or syntax errors. Ensure that no new linter warnings are introduced in the modified code.
*   **Clean Whitespace**: Always strip trailing whitespaces (including spaces on otherwise blank lines/lines with only spaces) from all modified files before committing changes. You can run `sed -i 's/[[:space:]]\+$//' <files>` or configure your editor to clean them up.
*   **Test Coverage for Code Changes**: Never change codebase logic or behavior without writing new tests or expanding existing unit tests to cover the modified/added paths.
*   **Pre-Refactor Testing**: If a large refactoring is planned or required, you must first add or verify baseline unit/integration tests that protect the existing behavior before changing the implementation.
*   **Single-Use Variables and Constants**: If a local variable or constant is used only once, do not create a variable or constant for it—embed the expression or literal directly (scoped to lines touched by the change, never as a repo-wide sweep). Top-of-file `require` statements always stay because they set package loading order. Exception: always keep `local gettext = require("gettext")` even when used only once, because `xgettext` in `update-po.sh` only extracts `gettext("...")` and skips `require("gettext")("...")`.
*   **Parameter Naming and `_` Usage**: Reserve `_` strictly for parameters that are truly unused. If a parameter is forwarded or passed to another function, name it explicitly (e.g. `arg`) rather than `_`. Never use `_` as a `gettext` alias.
*   **Module Privacy (`_` Prefix)**: A `_` prefix marks a function or method as private to its module. Production code must never call another module's `_`-prefixed function. If cross-module access is necessary, make the function public by dropping the leading `_`.
*   **Single Condition Check Location**: Keep each condition check in one owning function rather than duplicating the same check across callers; let the owning function check the condition and return a boolean if callers need the outcome.
*   **Delete Unused Code**: Deleting unused code is always preferred. Delete any function with no production caller (and its spec-only tests) rather than keeping or patching it; test-only helpers do not belong in production code.
*   **Error Handling and Invariant Assertions**: Do not use defensive programming (such as nil guards or swallowing unexpected errors) to silently mask uninitialized state or unexpected conditions. Assert internal invariants with `assert(...)`: "it can never fire" is not an argument against an assert, it is the reason it can be an assertion. Avoid `pcall` unless the exception is genuinely expected.
*   **File I/O Failure Policy**: External filesystem failures (disk full, read-only media, permission errors) are not internal invariants—never crash with `assert` on file writes. If an external write fails, display a `Notification` or `InfoMessage` and preserve the old version (never replace or delete the previous file with a partial or empty one). Always use atomic persistence helpers (`util.writeToFile`, `ffiUtil.copyFile`), which write to a `.new` file, fsync, close, and atomically rename over the target.
*   **Commit Message Conventions**:
    *   Write commit message descriptions in continuous paragraphs explaining *why* the change was made and what broke rather than listing changes in bullet points or numbered lists.
    *   If there is a known bug or issue, add `fix #<issue-id>` if the change fully resolves the issue, or `bug #<issue-id>` if it relates to the issue.
    *   Bundle unit tests and production logic together in the final commit so changes are never split into half-complete commits (`one issue per commit`). Implement tests and production code in separate steps to avoid self-fulfilling tests.
*   **Git History and Branch Hierarchy**:
    *   Never amend a commit that has already been pushed to `origin`. Only consider amending unpushed commits on `master` and `master.hotfix`; on all other branches, prefer adding new commits.
    *   **Four-Level Branch Hierarchy**:
        1.  **`master.hotfix` (Last Released Version)**: Only includes essential, urgent fixes for the released version. Fixes happen directly in `master.hotfix` and merge directly to all other branches (including `master`, feature branches, and `dev`). Never merge or fast-forward `master` (or any other branch) into `master.hotfix`.
        2.  **`master` (Upcoming Release)**: Staging for the upcoming release. Changes land on `master` via pull requests from feature branches once they are verified and ready. Merging `master` directly to feature branches and `dev` is always fine (avoiding redundant intermediate merge commits).
        3.  **Feature Branches (Individual Features)**: Branches dedicated to individual features or subsystems (e.g. `lua`, `new-libs`). Fixes for features land on their own feature branch with regression tests first before merging.
        4.  **`dev` (Integration Branch)**: Usually the integration merge of every active feature branch, except for specific experimental branches where stability is not yet assured (such as `new-libs`). Fixes never land directly on `dev`; only `dev`-only integration changes are committed directly on `dev`.
*   **VCS Push Policy**: Never push commits automatically to remote repositories. Keep changes local, and let the user perform the push, or only push when explicitly requested by the user.
*   **Symbolic Link Propagation (`lns.sh`)**: When adding or removing files from the `koreader/` directory, run the `./lns.sh` script to propagate the symbolic links to target device platform folders (e.g. `linux/`, `pw2/`, `legacy/`, etc.). You do not need to run `./lns.sh` if only modifying the content of an existing file.
*   **Tracking Removed Files**: When deleting files from the repository that were previously present under `koreader/`, update [remove-removed-files.sh](../remove-removed-files.sh) to include their paths so they can be cleaned up on target devices.
